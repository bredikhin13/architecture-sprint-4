### **Мотивация**

**Проблема: отсутствие контроля над системой**

На данный момент компания работает «вслепую» – команда узнаёт о проблемах только после того, как клиенты начинают жаловаться. Это приводит к:
- Потере клиентов и репутации – пользователи API (B2B) отказываются от сотрудничества, так как не могут доверять системе.
- Просроченным заказам – клиенты ждут свои изделия месяцами, а операторы не могут понять, почему заказ завис.
- Неэффективной работе команды разработки – программисты тратят время на поиск проблем вручную, вместо улучшения системы.
- Неоптимальному расходу ресурсов - без анализа ключевых метрик для серверов и баз данных непонятно текущее потребление ресурсов, поэтому приходится держать часть мощностей про запас.

**Как мониторинг помогает решить эти проблемы:**

Снижение числа потерянных заказов и жалоб клиентов
- Если заказ зависает – система автоматически отправляет уведомление, вместо того чтобы ждать жалобы клиента.
- Видно, на каком этапе заказ застрял и кто его должен обработать.

Предотвращение потерь клиентов и контрактов
- Если API отвечает слишком медленно, команда узнаёт об этом до того, как клиенты начнут отказываться от сотрудничества.
- Можно настроить SLA, чтобы B2B-партнёры были уверены в стабильности API.

Оптимизация серверных затрат
- Если сервер перегружен – можно увидеть это в реальном времени и добавить мощности.
- Исключается перерасход ресурсов (не нужно держать лишние серверы «на всякий случай»).

Повышение эффективности разработчиков
- Программисты тратят меньше времени на разбор сбоев, так как мониторинг сразу показывает проблемные места.
- Баги исправляются до того, как они вызовут массовые сбои.

**Как это работает:**

- Мы собираем метрики о работе всех ключевых компонентов (API, серверов, БД, RabbitMQ, MES).
- Если какой-то показатель выходит за рамки нормы, система автоматически уведомляет команду.
- В реальном времени видны узкие места (например, MES тормозит из-за долгих запросов к БД).
- Команда может оперативно устранять проблемы, а не разбираться с жалобами клиентов постфактум.

**Простой пример:** 

Сейчас клиенты B2B жалуются, что API медленно отвечает, но никто не знает, почему.  
С мониторингом можно будет сразу увидеть:
- Высокая нагрузка? (слишком много запросов).
- Слабый сервер? (не хватает CPU/RAM).
- Проблемы с БД? (медленные запросы).  

Быстро определив проблему, можно будет внести исправления до того, как клиенты откажутся от сервиса.

### **Выбор подхода к мониторингу**
Для разных частей системы применим разные методы:

| Подход                                                        | Где использовать              | Почему                                                 |
|---------------------------------------------------------------|-------------------------------|--------------------------------------------------------|
| RED                                                           | API, онлайн-магазин, CRM, MES | Контроль количества запросов, ошибок, времени отклика. |
| USE (Utilization, Saturation, Errors)                         | Серверы и БД                  | Определение загруженности CPU, памяти, соединений.     |
| Четыре золотых сигнала (latency, traffic, errors, saturation) | Общий мониторинг              | Позволяет следить за всей системой.                    |

### **Метрики для мониторинга**
Выбираем ключевые метрики для контроля работы системы.

**RabbitMQ**
- `Number of dead-letter-exchange letters` – сколько сообщений попало в DLQ. Если показатель растёт, значит заказы застревают и не доходят до CRM/MES.
- `Number of messages in flight` – сколько сообщений в обработке. сли число постоянно большое, значит очередь не обрабатывается вовремя.

**API (онлайн-магазин, CRM, MES)**
- `RPS (requests per second)` – частота запросов. Если RPS резко вырос, то возможна DDoS-атака или ошибка в клиентских системах.
- `HTTP 500 count` – количество серверных ошибок. Рост ошибок ухудшает пользовательский опыт. 
- `Response time (latency)` – время отклика. Высокое время отклика ухудшает пользовательский опыт.

**Серверы**
- `CPU % utilization` – загрузка CPU. Если CPU сервера выше 80-90%, он перегружен возможно из-за плохо написанного кода (циклы, утечки памяти) или большого количества запросов от клиентов.
- `Memory utilization` – использование памяти. Если память расходуется на 90-100%, возможен OOM.
- `Number of connections to DB` – количество соединений. Высокое число подключений может привести к замедлению работы базы данных.

**Базы данных**
- `Size of shop/MES DB` – размер БД. Если размер БД слишком большой, запросы могут выполняться медленнее.
- `Number of queries per second` – нагрузка на БД. При большом количестве запросов может увеличиться риск возникновения ошибок.

**MES (дашборд операторов)**
- `Time to load dashboard` – время загрузки первой страницы. Если страница MES загружается больше 5 секунд, операторы теряют время.
- `Cache hit ratio` – эффективность кеша. Если кеш используется слабо, сервер делает много лишних запросов в БД.

### **План действий**

1. Развернуть мониторинг
    - Использовать Prometheus + Grafana для API и серверов.
    - Включить OpenTelemetry для трейсинга запросов.

2. Настроить алертинг
    - Уведомления в Slack/Telegram при превышении порогов (например, 500+ ошибок за минуту).

3. Настроить дашборды
    - API метрики: RPS, HTTP 500, Latency.
    - **Системные метрики**: CPU, Memory, Disk usage.

4. Оптимизировать узкие места
    - Если API перегружено, то добавить rate limiting.
    - Если MES тормозит, то кешировать запросы к БД.
