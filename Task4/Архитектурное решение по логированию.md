### **Мотивация**

**Проблема: отсутствие централизованной системы логирования.**

Из-за отсутствия централизованной системы логирования компания сталкивается со следующим трудностями:

- Отсутствие централизованного хранения логов – данные разрознены между сервисами, что затрудняет диагностику.
- Ручной анализ ошибок – разработчики и операторы вынуждены искать причину проблемы в логах каждого сервиса отдельно.
- Длительное расследование инцидентов – поиск первопричины сбоя требует значительных временных затрат.
- Отсутствие исторических данных – нет возможности анализировать повторяющиеся сценарии отказов и оптимизировать систему.
- Невозможность оперативного реагирования – ошибки выявляются только после жалоб клиентов.

**Как централизованная система логирования поможет решить эти проблемы**

- Обеспечение единой системы хранения логов – все события фиксируются в одном месте.
- Сокращение времени на поиск причин инцидентов – операторы и разработчики могут быстро находить ошибки.
- Автоматическое выявление проблем – система оповещает о сбоях до появления жалоб клиентов.
- Оптимизация процессов – анализ исторических данных позволяет улучшить производительность сервисов.

### Системы, которые необходимо покрыть логами

Логирование будет реализовано во всех ключевых сервисах:
1. Онлайн-магазин
2. CRM
3. MES
4. RabbitMQ
5. API для B2B-клиентов

**Логи с уровнем INFO**
Данные логи помогут анализировать бизнес-процессы и контролировать выполнение операций.
- Изменение статуса заказа
    - Время события.
    - `order_id`.
    - `customer_id`.
    - Новый статус заказа.
- Создание заказа через API
    - Время запроса.
    - `request_id`.
    - `customer_id`.
    - `http_method`.
    - `response_time`.
- Передача данных между системами
    - Время передачи.
    - `queue_name`.
    - `message_id`.
    - `status` (успешно, повторная попытка, ошибка).
- Расчёт стоимости заказа в MES
    - Время начала и окончания расчёта.
    - `order_id`.
    - `processing_time`.

**Логи с уровнями WARN и ERROR**
Кроме логов INFO, будут собираться ошибки и предупреждения, чтобы своевременно выявлять проблемы.

WARN:
- Увеличенное время обработки заказа
    - `order_id`.
    - `expected_time`.
    - `actual_time`.
- Очередь сообщений переполнена
    - `queue_name`.
    - `message_count`.

ERROR:
- Ошибка при расчёте стоимости
    - `order_id`.
    - `exception_message`.
    - `stack_trace`.
- Ошибка базы данных при обработке заказа
    - `query_id`.
    - `error_code`.
    - `db_instance`.

## **Предлагаемое решение**

Для сбора, хранения и анализа логов будет использоваться ELK-стек. Он позволяет централизованно хранить и индексировать логи,
обеспечивает быстрый поиск по логам, поддерживает визуализацию и анализ данных и возможность настройки автоматического алертинга.

Сбор логов будет происходить из всех сервисов, после чего они будут отправляться в Logstash через Filebeat. Logstash нормализует данные и передаёт их в Elasticsearch.
После этого они станут доступны для визуализации и анализа в Kibana. При обнаружении системой аномалий или критических ошибок будут автоматически создаваться алерты.
Безопасность будет обеспечена с помощью существующего механизма авторизации и аутентификации на основе роли пользователя. 
Хранение данных будет оптимизировано, логи будут храниться 30 дней, затем архивироваться в S3 или другое дешевое хранилище. 
Чувствительные данные, например, персональные данные клиентов, будут маскироваться.
